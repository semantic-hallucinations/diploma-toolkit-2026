# Layout Methodology

Дата формализации: 2026-04-26.

Эта методика описывает, как раскладывать элементы так, чтобы диаграммы были
читаемыми и близкими к требованиям оформления записки. Автоматический layout
можно использовать как помощник, но финальные координаты в `.drawio` должны
быть явными и проверяемыми.

## Общая Модель

Для каждого профиля layout строится в четыре шага:

1. Оценить размер узлов по тексту, количеству строк и compartments.
2. Разложить узлы по профилю диаграммы.
3. Проложить ортогональные связи.
4. Посчитать качество layout и либо принять результат, либо попробовать другой
   вариант, либо вернуть ошибку с просьбой упростить диаграмму.

## Метрики Качества

Минимальный набор метрик:

- нет пересечения фигур;
- текст не выходит за фигуры;
- количество пересечений линий минимально;
- количество изломов минимально;
- длина линий не чрезмерна;
- направление главного потока соблюдено;
- aspect ratio подходит для вставки в A4;
- диаграмма читается при целевом размере;
- однотипные элементы выровнены;
- расстояния между элементами стабильны.

Для scoring можно использовать веса:

```text
score =
  crossings * 100
  + overlaps * 1000
  + bends * 5
  + long_edges * 2
  + label_overflows * 1000
  + aspect_penalty * 20
```

Если `overlaps > 0` или `label_overflows > 0`, результат нельзя принимать.

## ГОСТ-Блок-Схемы

Layout: собственная сетка, не произвольный graph layout.

Правила:

- основной поток сверху вниз;
- альтернативно слева направо, если схема явно горизонтальная;
- блоки одного потока выравниваются по центральной оси;
- ветви условия расходятся влево/вправо и возвращаются через merge point;
- циклы рисуются с обратной связью и обязательной стрелкой на обратном
  направлении;
- длинные переходы заменяются соединителями;
- все изломы под 90 градусов;
- стрелки на неосновных направлениях обязательны;
- количество пересечений должно быть равно нулю или объясняться соединителями.

Для строгого режима лучше не использовать Graphviz как финальный layout: он
может помочь черновиком, но ГОСТ-правила и соединители проще контролировать
своей сеткой.

## Sequence

Layout детерминированный:

- участники идут слева направо в порядке первого появления или по явному
  `order`;
- actor/external участники ставятся по краям;
- system/service/database участники внутри;
- lifeline - вертикальная пунктирная линия;
- каждое сообщение получает отдельную строку;
- synchronous call - сплошная стрелка;
- return - пунктирная стрелка;
- activation blocks добавляются только если они не ухудшают читаемость;
- alt/loop/opt рамки строятся как группы с отступами.

Это один из самых надежных профилей для автогенерации.

## Class

Layout комбинированный:

- наследование и реализации интерфейсов идут сверху вниз;
- базовые классы и интерфейсы выше;
- зависимые классы ниже;
- packages/modules группируются в swimlane-like области;
- ассоциации по возможности ортогональные;
- композиция/агрегация получают явные markers;
- для больших диаграмм лучше требовать явный `focus`, чтобы не рисовать весь
  проект.

Автоматически сгенерированную class diagram почти всегда нужно ограничивать
ключевыми классами.

## ERD

Layout:

- reference/lookup tables слева или сверху;
- core entities в центре;
- child/detail tables справа или снизу;
- many-to-many join tables между связанными сущностями;
- связи ортогональные;
- кардинальности ставятся у концов связей;
- nullable/PK/FK отображаются текстом в compartments.

Для диплома чаще нужен logical ERD, а не полный physical dump всех индексов.

## C4

Layout по уровню:

- `System Context`: пользователь слева, дипломная система в центре, внешние
  системы справа, внешние источники данных снизу или справа.
- `Container`: UI слева/сверху, API/backend в центре, database/storage справа
  или снизу, external services справа.
- `Component`: входящие adapters/controllers сверху или слева, domain/service
  layer в центре, repositories/gateways снизу или справа.
- `Deployment`: environments как группы, nodes внутри, containers внутри nodes.

C4 не надо стилизовать как маркетинговую картинку. Для записки лучше простой
черно-белый стиль с явными границами системы.

## Deployment

Layout:

- окружения разделяются группами: local/test/prod или client/server/cloud;
- network zones идут слева направо от клиента к backend и data layer;
- узлы показываются как nested containers;
- runtime artifacts внутри узлов;
- storage и databases отделяются от compute;
- внешние сервисы справа;
- связи ортогональные и подписанные протоколами, если это важно.

## ML Pipeline

Layout:

- источник данных слева;
- preprocessing/validation/feature engineering по центру;
- training/evaluation/model registry сверху или в основной цепочке;
- inference path можно вести отдельной нижней дорожкой;
- feedback/monitoring возвращается обратной связью через нижнюю линию;
- datasets/storage лучше рисовать как data/store shapes;
- операции - process shapes.

Для ML pipeline допустимо использовать ГОСТ-похожие формы, но не утверждать,
что это строгая схема по `ГОСТ 19.701-90`, если используются ML-специфичные
блоки вне стандарта.

## Use Case

Layout:

- system boundary - прямоугольник с названием системы;
- use cases - эллипсы внутри boundary;
- primary actors слева;
- secondary/external actors справа;
- actor-use-case связи прямые или ортогональные;
- include/extend связи пунктирные и подписанные;
- generalization актеров или use cases только если действительно нужна.

Use case диаграммы быстро становятся шумными. Лучше 5-12 use cases на рисунок.

## Автоматические Layout Engines

Возможные помощники:

- `ELK/elkjs` - сильный кандидат для layered/orthogonal layout и compound
  graphs.
- `dagre` - простой hierarchical layout для directed graphs.
- `Graphviz dot` - хорош для черновиков и графов зависимостей; `splines=ortho`
  дает ортогональные полилинии, но есть ограничения по labels/ports.

Решение: layout engine может предлагать координаты, но финальный `.drawio`
должен проходить наш validator. Для ГОСТ-блок-схем финальный layout лучше
делать вручную алгоритмом сетки.
