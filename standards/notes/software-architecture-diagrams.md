# Software Architecture Diagrams

Дата исследования: 2026-04-26.

Эта заметка про диаграммы для software/AI диплома: UML class/sequence/use-case,
ERD, BPMN, C4, блок-схемы алгоритмов, deployment, схемы данных, кода,
архитектуры и похожие виды рисунков.

## Статус Для Диплома БГУИР

`СТП 01-2024` явно описывает:

- обычные иллюстрации в пояснительной записке;
- графическую часть диплома;
- схемы по ЕСКД, включая структурные, функциональные, принципиальные,
  соединений, подключения, общие и расположения;
- диаграммы/графики функциональных зависимостей;
- схемы алгоритмов, программ, данных и систем по `ГОСТ 19.701-90`;
- плакаты для графического материала дипломных работ.

`СТП 01-2024` не делает UML, C4, BPMN, DMN, ERD, ArchiMate или SysML
обязательными стандартами для диплома. Для software/AI диплома их безопаснее
использовать как пояснительные рисунки в записке или как содержимое плаката,
если руководитель и нормоконтроль это принимают.

Если нужна формальная блок-схема алгоритма/программы/данных/системы, самый
безопасный вариант - `ГОСТ 19.701-90`.

## Практический Набор Для Software/AI Диплома

Обычно достаточно 5-8 хорошо выбранных диаграмм:

1. `C4 System Context` или простая контекстная диаграмма - пользователи,
   внешние системы и границы дипломной системы.
2. `C4 Container` - приложения, сервисы, база данных, очередь, model service,
   object storage, внешние API.
3. `C4 Component`, `UML Component` или `UML Package` - внутренние модули
   ключевого сервиса.
4. `UML Use Case` - цели акторов и границы функциональности.
5. `UML Sequence` - 1-3 ключевых сценария во времени.
6. `ERD` - структура базы данных или предметной области.
7. `UML Activity` или схема по `ГОСТ 19.701-90` - алгоритм, workflow,
   preprocessing/training/inference pipeline.
8. `UML Deployment` или C4 deployment - где система разворачивается.

Дополнительно можно добавить `UML State Machine`, ML/model architecture diagram,
data lineage, DFD/threat-model diagram или screen-flow, если это реально
объясняет проект.

## Каталог Диаграмм

### Требования И Предметная Область

- `UML Use Case` - акторы и цели использования системы. Хорош для раздела
  требований, но не заменяет текстовые сценарии.
- `Context diagram` - система в окружении пользователей, внешних сервисов и
  источников данных. Можно делать в стиле C4.
- `User journey` - путь пользователя по шагам. Уместен, если в дипломе важен
  UX или пользовательский процесс.
- `Screen flow / navigation map` - переходы между экранами приложения.
- `BPMN Process/Collaboration` - бизнес-процесс, роли, события, решения,
  сообщения между участниками.
- `DMN Decision Requirements Diagram` - решения, входные данные и знания,
  влияющие на решение. Уместно для правил, scoring, eligibility, routing.

### Архитектура ПО

- `C4 System Context` - место системы в окружении.
- `C4 Container` - крупные исполняемые части: frontend, backend, database,
  broker, model service, worker, storage.
- `C4 Component` - компоненты внутри одного контейнера.
- `C4 Code` - уровень классов/функций; в дипломе чаще лучше заменить
  `UML Class`, `UML Package` или короткой схемой модулей.
- `C4 Dynamic` - сценарий взаимодействия компонентов, облегченная альтернатива
  sequence diagram.
- `C4 Deployment` - окружения, nodes, containers, infrastructure.
- `UML Component` - компоненты, интерфейсы и зависимости.
- `UML Package` - пакеты, слои, namespace и зависимости кода.
- `UML Deployment` - узлы, runtime, артефакты и размещение.
- `High-level architecture diagram` - обычная boxes-and-arrows схема, если C4
  слишком формален. Нужны легенда и единый уровень абстракции.

### Взаимодействие И Поведение

- `UML Sequence` - обмен сообщениями во времени. Один из самых полезных видов
  для API, микросервисов, авторизации, обработки запроса, inference-flow.
- `UML Communication` - те же взаимодействия, но с упором на связи между
  участниками, а не на временную шкалу.
- `UML Activity` - поток работ, ветвления, параллельность, swimlanes.
- `UML State Machine` - состояния и переходы сущности или процесса: заявка,
  задача, заказ, training job, experiment, model version.
- `UML Interaction Overview` - обзор нескольких interaction/sequence сценариев
  через activity-like flow. Нужен редко.
- `UML Timing` - поведение во времени с временными ограничениями. Обычно нужен
  только для realtime/embedded.
- `Event flow / event storming-style diagram` - события предметной области и
  реакции системы. Можно использовать как поясняющий рисунок.
- `Queue/topic topology` - producers, consumers, topics, exchanges, queues.
  Полезно для асинхронной архитектуры.

### Данные И Базы Данных

- `Conceptual ERD` - сущности предметной области без технических таблиц.
- `Logical ERD` - сущности, атрибуты, ключи, связи, кардинальности.
- `Physical DB schema` - реальные таблицы, индексы, foreign keys.
- `Crow's foot ERD` - практичная нотация кардинальностей для реляционных БД.
- `IDEF1X` - более формальная нотация data modeling; использовать только если
  она действительно знакома руководителю/кафедре.
- `Data Flow Diagram (DFD)` - процессы, хранилища данных, внешние сущности и
  потоки данных. Полезно для анализа движения данных и threat modeling.
- `Data lineage` - путь данных от источника до отчета/model inference.
- `Data pipeline` - ingestion, validation, preprocessing, feature engineering,
  storage, training, inference.
- `Ontology / knowledge graph diagram` - классы понятий и связи, если тема
  связана с знаниями, графами или семантикой.

Важно: у ERD нет одного универсального современного стандарта, который был бы
прямым аналогом UML. Можно использовать crow's foot, IDEF1X или ERD-синтаксис
Mermaid/PlantUML, но не смешивать нотации в одной диаграмме.

### Внутреннее Устройство Кода

- `UML Class` - ключевые классы, интерфейсы, атрибуты, операции, наследование,
  ассоциации, агрегация/композиция. Не стоит генерировать диаграмму всех
  классов проекта, если она становится нечитаемой.
- `UML Object` - конкретные объекты и связи в момент времени. Полезно редко.
- `Module dependency graph` - зависимости модулей/пакетов.
- `Call graph` - кто какие функции вызывает в критичном участке.
- `Control-flow graph` - ветвления и переходы внутри сложного алгоритма.
- `ГОСТ 19.701` flowchart - формальная схема алгоритма, программы, данных или
  системы.
- `Nassi-Shneiderman diagram` - структурограмма алгоритма без стрелок. Для
  диплома обычно избыточна, но может быть понятной для компактного алгоритма.
- `Decision table/tree` - правила принятия решений; для формальной нотации
  решений можно смотреть DMN.
- `API map` - endpoints, consumers, contracts, external APIs.

### Развертывание, Эксплуатация И Безопасность

- `UML Deployment` или `C4 Deployment` - серверы, контейнеры, runtime,
  networks, volumes, databases, внешние сервисы.
- `Infrastructure/network topology` - сети, подсети, балансировщики, firewall,
  VPN, storage, observability.
- `CI/CD pipeline` - build, test, image, deploy, migrate, rollback.
- `Runtime sequence` - что происходит при запросе в production.
- `Threat model / trust boundary diagram` - границы доверия, внешние акторы,
  sensitive data, потенциальные угрозы.
- `Data privacy flow` - где появляются персональные/чувствительные данные,
  где они хранятся и кто имеет доступ.

### AI/ML Специфичные Диаграммы

- `ML/data pipeline` - сбор данных, очистка, разметка, preprocessing,
  feature engineering, split, training, evaluation, inference.
- `Model architecture diagram` - слои модели, encoder/decoder, embeddings,
  heads, loss, output.
- `Training workflow` - dataset version, experiment, hyperparameters, metrics,
  artifacts, model registry.
- `Inference pipeline` - request, validation, preprocessing, model call,
  postprocessing, response, logging.
- `MLOps lifecycle` - data drift, retraining trigger, validation, deployment,
  monitoring.
- `Experiment tracking flow` - как сохраняются параметры, метрики, артефакты и
  версии моделей.

## UML

UML 2.5.1 - основной формальный источник для class, sequence, use-case,
activity, state, component, deployment и связанных диаграмм.

UML делит диаграммы на структурные и поведенческие.

Структурные:

- `Class diagram` - классы, интерфейсы, атрибуты, операции, наследование,
  ассоциации, агрегация/композиция.
- `Object diagram` - конкретные объекты и связи в момент времени.
- `Package diagram` - пакеты, модули, слои и зависимости между ними.
- `Component diagram` - компоненты, интерфейсы, зависимости.
- `Composite structure diagram` - внутренняя структура класса/компонента.
- `Deployment diagram` - узлы, runtime, артефакты, размещение.
- `Profile diagram` - расширения UML. Для диплома обычно не нужен.

Поведенческие:

- `Use Case diagram` - акторы и цели использования системы.
- `Activity diagram` - поток работ, ветвления, параллельность.
- `State Machine diagram` - состояния и переходы.
- `Sequence diagram` - обмен сообщениями между участниками во времени.
- `Communication diagram` - взаимодействия с упором на связи участников.
- `Interaction Overview diagram` - обзор нескольких interaction-сценариев.
- `Timing diagram` - временное поведение.

Для диплома по ПО/ИИ чаще всего реально нужны: use-case, class/package,
component, sequence, activity, state machine, deployment.

## BPMN И DMN

`BPMN 2.0.2` подходит, если надо описать бизнес-процесс или организационный
workflow: кто что делает, какие события запускают процесс, где решения,
параллельные ветки, сообщения между участниками.

Основные виды BPMN-диаграмм:

- process/orchestration diagram - процесс внутри одной организации/пула;
- collaboration diagram - взаимодействие участников через message flow;
- choreography diagram - обмен сообщениями без показа внутренних процессов
  участников;
- conversation diagram - крупные коммуникации между участниками.

`DMN` дополняет BPMN там, где важна логика принятия решений: decision
requirements diagram, decision tables, business knowledge models, input data.
Для диплома это полезно, если система принимает решения по набору правил или
моделей.

## C4

C4 - не официальный ГОСТ/ISO, но очень практичная нотация для архитектуры ПО.
Она хорошо подходит для диплома, потому что объясняет систему на разных уровнях
детализации.

Основные диаграммы:

- `System Context` - система, пользователи, внешние системы.
- `Container` - веб-приложение, backend, БД, broker, model service, object
  storage и т. п.
- `Component` - внутренние компоненты контейнера.
- `Code` - классы/интерфейсы/функции; обычно лучше заменить UML class/package.

Дополнительные:

- `System Landscape` - несколько систем в ландшафте.
- `Dynamic` - сценарий взаимодействия компонентов.
- `Deployment` - инфраструктура и размещение контейнеров.

Для диплома обычно достаточно `Context + Container + 1 Component`.

## ГОСТ 19.701 И Блок-Схемы Кода

Если надо показать алгоритм как формальную блок-схему, ориентироваться лучше на
`ГОСТ 19.701-90`.

В `СТП 01-2024` перечислены:

- схема данных;
- схема программы;
- схема работы системы;
- схема взаимодействия программ;
- схема ресурсов системы;
- схема алгоритма работы технического устройства/системы.

Практические правила:

- основной поток сверху вниз и слева направо;
- стрелки можно не ставить только для основного направления;
- для остальных направлений стрелки обязательны;
- длинные переходы лучше делать через соединители;
- не смешивать произвольные фигуры с ГОСТ-символами, если схема заявлена как
  формальная.

Для кода часто лучше использовать не "блок-схему всего приложения", а 1-2
схемы ключевых алгоритмов.

## ArchiMate И SysML

`ArchiMate` полезен для enterprise-level архитектуры: бизнес-слой,
application-layer, technology-layer, мотивация, стратегия, миграция. Для
студенческого software/AI диплома чаще всего избыточен, но может быть полезен,
если тема про информационную систему в организации.

`SysML` полезен для системной инженерии: требования, структура, поведение,
параметры, верификация. Для чистого ПО обычно избыточен; для cyber-physical,
robotics, IoT, embedded или сложных технических систем может быть уместен.

## Инструменты И Экспорт

Для диплома лучше хранить диаграммы как исходный текст или модель, а в LaTeX
подключать готовый экспорт:

- Mermaid - быстро для flowchart, sequence, class, state, ERD, C4-like,
  user journey и других диаграмм;
- PlantUML - удобно для UML, C4, sequence, class, component, state, deployment;
- Structurizr DSL - удобно для C4 и architecture-as-code;
- diagrams.net/draw.io - удобно для ручных схем, если нужен полный контроль.

Практические правила:

- экспортировать в vector PDF/SVG, если возможно;
- если используется PNG, брать достаточное разрешение для A4;
- не вставлять скриншоты редактора диаграмм;
- все подписи на рисунке писать теми же терминами, что и в тексте диплома;
- для нестандартной нотации добавлять легенду.

## Рекомендации По Выбору

Для типичного диплома по ИИ:

- `Use Case` - если есть разные пользователи и пользовательские цели.
- `C4 Context` - чтобы быстро объяснить место системы.
- `C4 Container` - чтобы объяснить сервисы, БД, модель, очереди, внешние API.
- `Sequence` - для 1-3 ключевых сценариев: регистрация, inference, обучение,
  обработка запроса.
- `ERD` - если есть БД или предметная модель.
- `Activity` или `ГОСТ 19.701` - для алгоритма обработки данных/обучения.
- `State Machine` - если есть сущность с состояниями.
- `Deployment` - если есть Docker/cloud/server/edge deployment.
- `ML/data pipeline` - если важны данные, обучение и inference.
- `Threat model / DFD` - если есть персональные данные, внешние интеграции или
  существенные риски безопасности.

Для пояснительной записки лучше подписывать так:

- `Рисунок 2.3 - Диаграмма вариантов использования системы`;
- `Рисунок 3.1 - Контекстная диаграмма системы`;
- `Рисунок 3.2 - Контейнерная диаграмма системы`;
- `Рисунок 3.3 - Диаграмма последовательности обработки запроса`;
- `Рисунок 3.4 - ER-диаграмма базы данных`;
- `Рисунок 3.5 - Схема алгоритма предварительной обработки данных`;
- `Рисунок 3.6 - Диаграмма развертывания системы`;
- `Рисунок 3.7 - Конвейер обучения модели`.

## Общие Правила Качества

- Одна диаграмма - один вопрос.
- Не смешивать C4, UML, BPMN, ERD и ГОСТ-символы на одном рисунке.
- В заголовке или подписи указывать тип диаграммы.
- Для нестандартной нотации давать легенду.
- Все элементы на диаграмме должны называться теми же терминами, что и в тексте.
- На каждую диаграмму нужна ссылка в тексте до или рядом с рисунком.
- Диаграмма должна быть читаемой в итоговом PDF без увеличения.
- Не вставлять автогенерированную диаграмму всего кода, если она не помогает
  читателю.
- Не перегружать диплом редкими нотациями: лучше меньше диаграмм, но каждая
  отвечает на конкретный вопрос проверяющего.
